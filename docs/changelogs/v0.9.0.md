# v0.9.0 Changelog

Version 0.9.0 is a **breaking release** that changes three fundamental areas of the library:

1. **Event Bus State Propagation.** The Digital Twin State does not travel anymore as a single, complete `DigitalTwinState` on the event bus. It is split into a **description** (the structure of the state, with a unique id) and **values** (a delta with only the values that changed), published on two separate topics. Every component that observes the state keeps its own, always up to date, local copy. This drastically reduces what circulates inside the Digital Twin. **All the Digital Twins written for previous versions must be migrated** (see [Migration from 0.8.1](#migration-from-081)).
2. **A new declarative Query System.** The request-type based `QueryRequest` is replaced by an immutable `Query` object (resource, filter, sorting, paging, aggregation, timeout) that is translated by the storage into its own native language, so only the needed records are returned. The state is stored and queried as description + values.
3. **State Filters.** Digital Adapters and Augmentation Functions can choose *when* they are notified of a values update (trigger filter) and *which part* of the values they receive (content filter). The description is never filtered. The Storage Manager does not filter: it always saves the description and the complete values.

> **⚠️ Breaking changes at a glance.** Almost every component that touches the Digital Twin State must be updated:
>
> - **Compile errors** (code that does not compile anymore): Shadowing Functions (`DigitalTwinModel`), Digital Adapters, Augmentation Functions and custom `AugmentationFunctionHandler`, custom `WldtStorage` / `QueryManager`, `LifeCycleListener` implementations, event bus subscribers of the state events, code that uses `QueryRequest`.
> - **Silent behaviour changes** (the code still compiles but behaves differently, see [Behaviour changes without compile errors](#behaviour-changes-without-compile-errors)): the last invocation of an action is not recorded automatically anymore, `STARTED` is notified before the adapters run, `observeState` / `observeEventNotifications` are now honoured, stored states and their counts have a different meaning, storage metrics changed.
>
> The table [Breaking changes](#breaking-changes) lists every change with its **impact**, and [Migration from 0.8.1](#migration-from-081) gives the steps to follow.

Key updates:

- **Two state topics** — `dt.state.description.update` (the complete new description, published **only if the structure really changed**) and `dt.state.values.update` (only the changed values). `dt.state.update` and the complete state on the bus do not exist anymore
- **`DigitalTwinStateDescription` has a unique id** `<creationTimestamp>_<numSeq>` and `DigitalTwinStateValues` always carries the id of the description it belongs to
- **`DigitalTwinStateManager` never returns the complete state** — `getDigitalTwinStateDescription()` and `getDigitalTwinStateValues()` replace `getDigitalTwinState()`
- **Last invocation of actions / last notification of events are values of the state**, written inside state transactions (`notifyActionExecuted`, `notifyDigitalTwinStateEvent`)
- **Local copy of the state in every observer** — new `DigitalTwinStateReplica` (`applyDescriptionEvent` / `applyValuesEvent` return whether the event has been applied, `applyNextPendingValues()` drains the values that arrived before their description), with `DigitalTwinStateManager.getDescriptionChanges(event)` / `getValuesChanges(event)` to read the changes carried by an event
- **Digital Adapter** — `onStateUpdate` removed; `onStateDescriptionUpdate` / `onStateValuesUpdate` are the abstract state callbacks; content and trigger filters are set with `observeDigitalTwinState(filter[, changeFilter])`, typically in `onDigitalTwinSync`
- **Storage Manager and storages** — description and values are saved separately (`saveDigitalTwinStateDescription(description, changes)` / `saveDigitalTwinStateValues(values, valuesDelta, changes)`), the complete state is queried as a description with its values (`DigitalTwinStateHistoryRecord`); the Storage Manager never filters: it always saves the description and the complete values
- **Augmentation Functions** — `onStateDescriptionUpdate` / `onStateValuesUpdate` replace `onStateUpdate`; the context has description and values; the abstract `AugmentationFunctionHandler` applies the filters of each function and calls two per-function hooks
- **`Query` replaces `QueryRequest`** — built with `Query.on(resourceType)`, with filters, sorting, `limit`/`offset`, aggregations, total count and timeout
- **`WldtStorage` is query-driven** — the ~60 per-resource getters are replaced by a single `execute(Query)` method
- **`QueryResult` always returns records** — typed (`QueryResult<T extends StorageRecord>`) and built with `success(...)` / `failure(...)`
- **Filters and aggregations** — new `filter` and `aggregation` sub-packages, plus an in-memory evaluator used by `DefaultWldtStorage`
- **Query timeout** — configurable on the `Query` and on the `QueryExecutor`; expired queries are skipped by the `StorageManager`
- **`observeState` / `observeEventNotifications` are now honoured** on the stateful push path
- **Optional query refresh on every values update** for stateful functions (`refreshQueryOnStateUpdate`)
- **Removal of the constructors deprecated in 0.8.1** (type-only constructors of State and Physical Asset properties and events)
- **Event bus robustness** — a failing subscriber no longer stops the delivery of the following events to the same subscriber
- **Life cycle order** — `STARTED` is published before the Physical and Digital Adapters are executed, so `BOUND` can never precede it (the start callbacks of the adapters are therefore called before the adapters run)
- **Storage monitoring** — new metrics for the writes of the state description; `storage_write_dt_state_*` now count the values writes

## Behaviour changes without compile errors

These changes do **not** produce compile errors: code written for 0.8.1 builds, but behaves differently. Review each of them.

| What changes | Before (0.8.1) | Now (0.9.0) | What to do |
|---|---|---|---|
| Last invocation of an action | Updated by the library when a Digital Action was received | **Never updated automatically** | Call `notifyActionExecuted(actionKey[, instant])` inside a state transaction when the Shadowing Function considers the action executed |
| Notification of a state event | `notifyDigitalTwinStateEvent(...)` could be called outside a transaction | Throws `WldtDigitalTwinStateEventNotificationException` outside a transaction; published at commit | Wrap the call in `startStateTransaction()` / `commitStateTransaction()` |
| Life cycle order | `BOUND` could be published before `STARTED` (race with the adapters) | `STARTED` is **always** published before the adapters are executed, then `BOUND` | Nothing, unless the code relied on the old order |
| Start callback of the adapters | `onDigitalTwinStart()` / `onStart()` called while the adapters were already running | Called **before** the adapters run (before `onAdapterStart()`); a way to exploit it will be defined in the future | Do not initialize adapter resources there: use `onAdapterStart()` |
| `observeState` / `observeEventNotifications` of a function | `observeState = false` only affected the context of start / stop / execute; `observeEventNotifications` was ignored | Both are honoured on the push path | Review functions that set them to `false` |
| Number of values updates | One state update per transaction | A notified event or an executed action adds a **values** update (the last notification / invocation is a value of the state) | Review stateful functions and adapters without filters that react to every update |
| State events delivered to the subscribers | Complete state at every update | Description (only on a real structural change) and values **delta** (possibly with an empty body), two independent topics | Keep a `DigitalTwinStateReplica` instead of reading the body as the complete state |
| Storage of the state | One complete state record at every update | Description saved at every structural change, **complete** values saved at every values update, never filtered | Query `DIGITAL_TWIN_STATE_DESCRIPTION` / `DIGITAL_TWIN_STATE_VALUES` for counts; read `DIGITAL_TWIN_STATE` as a `DigitalTwinStateHistoryRecord` |
| Removal of a property, relationship, action or event | A state update with the new state | A description update only; **no** values callback (the local copies drop the value) | React to removals in `onStateDescriptionUpdate` |
| Metrics of the storage and of the Digital Adapter | `storage_write_dt_state_*` counted the state writes | They count the values writes; the description writes have their own metrics | Update dashboards and alerts |

## New: Event Bus State Propagation

### The two state events

Every committed state transaction publishes, in this order, up to two events (and then the notifications of the events notified in the transaction):

| Event | Topic | Published when | Body | Metadata |
|---|---|---|---|---|
| Description update | `dt.state.description.update` | The structure of the state **really changed**: the new description is compared structurally with the previous one (an update that leaves the structure identical publishes nothing) | The **complete** new `DigitalTwinStateDescription` | `DT_STATE_DESCRIPTION_UPDATE_METADATA_PREVIOUS_DESCRIPTION` (previous description), `DT_STATE_DESCRIPTION_UPDATE_METADATA_CHANGE_LIST` (changes that alter the structure) |
| Values update | `dt.state.values.update` | The transaction contains at least one change that produces a values update (see *Which changes alter what*) | A `DigitalTwinStateValues` **delta**: only the values that changed | `DT_STATE_VALUES_UPDATE_METADATA_PREVIOUS_VALUES` (previous values of the same resources), `DT_STATE_VALUES_UPDATE_METADATA_CHANGE_LIST` (changes that alter the values) |

`WldtEventTypes.DT_STATE_DESCRIPTION_UPDATE_MESSAGE_EVENT_TYPE` and `DT_STATE_VALUES_UPDATE_MESSAGE_EVENT_TYPE` (also `DigitalTwinStateManager.getStateDescriptionUpdateWldtEventMessageType()` / `getStateValuesUpdateWldtEventMessageType()`) are the topic constants. The topics of the event notifications (`dt.state.event.notification.*`) are unchanged.

What goes in the values delta:

- a property added or whose value changed: its new value; a property whose value is **unchanged** is not in the body (an update with the same value is still in the change list, and the event is published with an empty body and a new evaluation instant)
- a relationship added or with changed instances: the **complete** list of the instances of that relationship
- the last invocation of the actions / last notification of the events triggered in the transaction
- nothing for a removed property, relationship, action or event: the removal is **not** a values update, it travels only in the description event; every component that keeps a local copy drops the value when it applies the new description (so no values callback is invoked for a removal)
- a relationship instance added or removed: the complete, updated list of the instances of that relationship (the description does not change, so this is the only event that carries the removal of an instance)

### Description id

`DigitalTwinStateDescription.getId()` is `<creationTimestamp>_<numSeq>`: the epoch milliseconds of the creation of the `DigitalTwinStateManager` followed by a sequence number that starts from 0 (the initial, empty description) and grows every time the structure really changes. A transaction that changes several resources produces one new description. `DigitalTwinStateValues.getDescriptionId()` is the id of the description the values belong to: `DigitalTwinStateManager.getDigitalTwinStateValues()` always uses the id of the current description.

### Last invocation and last notification are values of the state

The last invocation of each action and the last notification of each event are part of the values and travel in the values update. They are written inside a transaction as a `DigitalTwinStateChange` with `OPERATION_UPDATE_VALUE` on an `ACTION` / `EVENT` resource (`getValueInstant()` carries the instant):

- `notifyDigitalTwinStateEvent(notification)` — requires a transaction; the notification is published **at commit time**, after description and values; a rolled back transaction publishes nothing; the event key must be defined in the state
- `notifyActionExecuted(actionKey[, executionInstant])` — new, requires a transaction. The invocation of a Digital Action does **not** update the timestamp anymore: the Shadowing Function calls this method when it considers the action executed

```java
this.digitalTwinStateManager.startStateTransaction();
this.digitalTwinStateManager.notifyActionExecuted("set-temperature-action-key");
this.digitalTwinStateManager.notifyDigitalTwinStateEvent(new DigitalTwinStateEventNotification<>("overheating", "critical", System.currentTimeMillis()));
this.digitalTwinStateManager.commitStateTransaction();
```

### Local copy of the state: `DigitalTwinStateReplica`

Digital Adapters, the Storage Manager and the Augmentation Function Handlers keep a **complete and never filtered** local copy of the description and of the values, initialized at synchronization time and updated at every event (`DigitalTwinStateReplica`, package `it.wldt.core.state`, available to custom components too). The delta of the values is merged with the complete values (`DigitalTwinStateValues.applyUpdate`) and a new description realigns the values to its id.

The public API of `DigitalTwinStateReplica` (all methods are `synchronized`; the caller holds `synchronized (replica)` around apply + read when it needs a consistent view):

| Method | Description |
|---|---|
| `seed(description, values)` / `clear()` / `isSeeded()` | Initialize the copy at synchronization time, drop it at un-synchronization, check if it is initialized |
| `boolean applyDescriptionEvent(WldtEvent<?>)` | Applies a description event: `true` if applied; `false` for a description that is not newer than the current one or that belongs to another state. After it the waiting values events must be drained |
| `boolean applyValuesEvent(WldtEvent<?>)` | Applies a values event: `true` if applied; `false` if it is kept waiting for its description, if it is already included in the seeded values, or if it belongs to another state |
| `WldtEvent<?> applyNextPendingValues()` | Applies the next waiting values event and **returns it**, `null` when there is none (or the next one still waits for its description). Call it in a loop after a description event |
| `getDescription()` / `getValues()` | The complete local copy (never filtered); `getPendingValuesCount()` counts the values waiting for their description |
| `DigitalTwinStateManager.getDescriptionChanges(event)` / `getValuesChanges(event)` | Static helpers (never `null`): the changes carried in the metadata of a description / values event |

```java
DigitalTwinStateReplica replica = new DigitalTwinStateReplica();
replica.seed(description, values);                    // at synchronization time

synchronized (replica) {
    if (replica.applyValuesEvent(wldtEvent))
        process(replica.getValues(), DigitalTwinStateManager.getValuesChanges(wldtEvent));

    if (replica.applyDescriptionEvent(wldtEvent)) {
        process(replica.getDescription(), DigitalTwinStateManager.getDescriptionChanges(wldtEvent));

        WldtEvent<?> pendingEvent;
        while ((pendingEvent = replica.applyNextPendingValues()) != null)
            process(replica.getValues(), DigitalTwinStateManager.getValuesChanges(pendingEvent));
    }
}
```

The two topics are delivered independently, so the values of a new description can arrive before the description itself. In that case they are kept in a list, in arrival order: when the description arrives it is applied first, then the waiting values are processed one at a time in the order they arrived (a warning is logged if they wait too long, nothing is discarded). Values that refer to an older description are applied anyway.

### Filters

- The **description is never filtered**, anywhere: Digital Adapters, the Storage Manager and Augmentation Functions always receive the complete new description at every structural change.
- `DigitalTwinStateFilter` (content, by name on properties, actions, events and relationships) and `DigitalTwinStateChangeFilter` (trigger, by operation, resource type and name) apply only to the values. The values callback is invoked if at least one change passes both; the delivered values are the complete values limited by the content filter. The local copy is always updated, whatever the filters.
- `DigitalTwinStateFilter.isDescriptionChange(change)` / `isValueChange(change)` classify the changes on the operation first (see *Which changes alter what*): the trigger of an action or event (`OPERATION_UPDATE_VALUE`) is a value change only, the removal of a property, relationship, action or event is a description change only.
- Consequence: a trigger rule with `OPERATION_REMOVE` on a property, relationship, action or event never fires a values callback (the removal is delivered by `onStateDescriptionUpdate`, which is never filtered); `OPERATION_REMOVE` on `RELATIONSHIP_INSTANCE` does.

### Digital Adapter

- `observeDigitalTwinState(filter[, changeFilter])` sets the content and trigger filters (typically in `onDigitalTwinSync`, where the description is available, so they are active from the first update) and `clearStateFilter()` removes them
- `onStateDescriptionUpdate(description, descriptionChanges)` — at every structural change, always complete
- `onStateValuesUpdate(values, relevantChanges)` — the **complete** values of the local copy (limited by the content filter), only if at least one change passes the filters
- `getDigitalTwinStateDescription()` / `getDigitalTwinStateValues()` — protected accessors to the complete local copy

### Storage

- `WldtStorage.saveDigitalTwinStateDescription(description, changes)` and `saveDigitalTwinStateValues(values, valuesDelta, changes)` (the complete values, the delta carried by the values event, `null` after a description removal, and the change list); the Storage Manager always saves the description and saves the **complete** values of its local copy (with the id of the description and the change list) at every values update, without any filter. After a description that contains a removal it saves the values aligned to the new description too (no values event is published for a removal)
- The Storage Manager does **not** filter: every description event saves the description and every values event saves the complete values of the local copy
- New resources `QueryResourceType.DIGITAL_TWIN_STATE_DESCRIPTION` (`DigitalTwinStateDescriptionRecord`) and `DIGITAL_TWIN_STATE_VALUES` (`DigitalTwinStateValuesRecord`); `DIGITAL_TWIN_STATE` returns the complete state as a **single** `DigitalTwinStateHistoryRecord` that maps every selected description (by description id) to the values stored for it in the selected interval (`getEntries()`, `getEntry(id)`, `getValuesList(id)`)
- Filters, sorting, limits and aggregations on `DIGITAL_TWIN_STATE` work on the fields of both description and values (`QueryFieldNames.DESCRIPTION_ID`, `values.propertyValues.<key>`, `description.<field>`, ...); `limit`, `offset` and `total` count the values (the selected rows, before the grouping by description)
- `StorageStats.getStateValuesVariationStats()` (renamed from `getStateVariationStats()`) and `getStateDescriptionVariationStats()`; `IWldtEventObserverListener` has `onStateDescriptionEvent`, `onStateValuesEvent`, `onStateEventNotification`

```java
// The complete state in an interval: one record that maps descriptions to their values
DigitalTwinStateHistoryRecord history = queryExecutor.syncQueryExecute(
        Query.on(QueryResourceType.DIGITAL_TWIN_STATE)
                .where(and(gte(QueryFieldNames.TIMESTAMP, from), lt(QueryFieldNames.TIMESTAMP, to)))
                .build())
        .as(DigitalTwinStateHistoryRecord.class).first();

for (DigitalTwinStateHistoryEntry entry : history.getEntries().values())
    logger.info("{}: {} values", entry.getDescriptionId(), entry.getValuesList().size());

// Average temperature for each description
Query stats = Query.on(QueryResourceType.DIGITAL_TWIN_STATE)
        .aggregate(groupBy(QueryFieldNames.DESCRIPTION_ID), count().as("count"), avg("values.propertyValues.temperature").as("avg"))
        .build();
```

### Augmentation Functions

- `StatefulAugmentationFunction.onStateDescriptionUpdate(DigitalTwinStateDescription)` — every structural change, never filtered
- `StatefulAugmentationFunction.onStateValuesUpdate(DigitalTwinStateValues)` — the complete values (limited by the content filter), only if at least one change passes the trigger and content filters; without filters it is invoked at every values update
- `AugmentationFunctionContext.getDigitalTwinStateDescription()` (always complete) and `getDigitalTwinStateValues()` (limited by the content filter) in the context of start, stop and execute
- The `AugmentationFunctionHandler` does not filter: it keeps the complete local copy; the filters are applied for each function. `DigitalTwinStateFilterUtils.filterValues(values, contextRequest)` replaces `filterState`

### Which changes alter what

| Change resource type | Description | Values |
|---|---|---|
| Change | Description update | Values update |
|---|---|---|
| `PROPERTY`, `RELATIONSHIP` with `OPERATION_ADD` / `OPERATION_UPDATE` | yes | yes (the value / the instances) |
| `PROPERTY`, `RELATIONSHIP`, `ACTION`, `EVENT` with `OPERATION_REMOVE` | yes | **no** (the local copies drop the value when they apply the description; no values callback) |
| `ACTION`, `EVENT` with `OPERATION_ADD` / `OPERATION_UPDATE` | yes | no (they carry no value) |
| `OPERATION_UPDATE_VALUE` (property value, last invocation of an action, last notification of an event) | no | yes |
| `RELATIONSHIP_INSTANCE` with `OPERATION_ADD` / `OPERATION_REMOVE` | no | yes (the complete list of the instances) |

A change is published in the description event only if the structure really changed, so for example `updateProperty(...)` with an identical structure produces a values update (the property value) but no description update.

## New: Query System

### `Query`

Immutable description of a query created with the builder `Query.on(resourceType)`: filter, sorting (`SortCriterion`), `limit` / `offset`, aggregation, `withTotal` and `timeout`. `refresh()` returns a copy with a new `requestId`, useful to re-run the same query periodically.

### Filters and aggregations

| Package | Classes |
|---------|---------|
| `it.wldt.storage.query.filter` | `Filter`, `ComparisonFilter`, `AndFilter`, `OrFilter`, `NotFilter`, `FilterOperator`, `FilterVisitor`, `FilterFactory` (`eq`, `gte`, `and`, ...) |
| `it.wldt.storage.query.aggregation` | `Aggregation`, `AggregationGroupBy`, `AggregationMetric`, `AggregationFunction`, `AggregationPart`, `AggregationFactory` (`groupBy`, `count`, `avg`, ...) |

`QueryFieldNames` lists the fields usable in filters, sorting and aggregations. The result of an aggregation is an `AggregationRecord` (package `it.wldt.storage.model`), holding the group-by values and the computed metrics with typed getters (`getString`, `getLong`, `getDouble`).

`FilterVisitor` allows a custom storage to translate the filter tree into the native query language of its backend (SQL, MongoDB, ...).

### Results

`QueryResult<T extends StorageRecord>` always contains a list of records (`getItems()`), the optional total number of matches, the status and the error message. Helpers: `as(Class)`, `first()`, `last()`.

### Timeouts

- `QueryExecutor.DEFAULT_QUERY_TIMEOUT_MS` is 5000 ms; a new constructor `QueryExecutor(digitalTwinId, queryExecutorId, defaultTimeoutMs)` customizes it
- A query overrides it with `Query.Builder.timeout(long)`
- Timeouts and errors are reported as failed `QueryResult`
- The `StorageManager` **skips** queries whose timeout already expired (nobody is waiting for the result), so a backlog of abandoned queries does not delay writes and other queries
- If no `QueryManager` is set, the `StorageManager` now answers with a failed `QueryResult` instead of leaving the caller waiting

### Custom storages

A custom `WldtStorage` implements `execute(Query)` and translates the query to its backend, plus `saveDigitalTwinStateDescription` and `saveDigitalTwinStateValues(values, valuesDelta, changes)`. `DefaultWldtStorage` delegates to the new `InMemoryQueryEvaluator` (package `it.wldt.storage.query.inmemory`), which can also be reused by storages that have no native query engine. For `DIGITAL_TWIN_STATE` the default storage takes a snapshot of the stored descriptions and values and delegates to `InMemoryDigitalTwinStateQuery`, that joins every values record with its description in an internal row (so filters, sorting and aggregations are evaluated on one values record at a time) and groups the selected rows in the single `DigitalTwinStateHistoryRecord`. See `docs/storage_query_system.md`.

## New: State Filters for Augmentation Functions

Until 0.8.1 every `dt.state.update` was pushed, with the complete state, to every running stateful function. Two optional filters are now available in `AugmentationFunctionContextRequest`. They are **disabled by default**: with no filter every values update is delivered with the complete values. They apply only to the **values**; the description is never filtered.

### 1. Trigger filter (stateful functions only)

`DigitalTwinStateChangeFilter` rules decide *when* a values update is pushed. A rule has optional criteria on **operation**, **resource type** and **resource name** (empty criterion = wildcard, non-empty criteria are AND-ed). The update is pushed if **any** change of the update matches **any** rule; if the update carries no change list, it is not pushed.

```java
DigitalTwinStateChangeFilter.onPropertyValueUpdate("temperature", "humidity");
DigitalTwinStateChangeFilter.onResources("near");
DigitalTwinStateChangeFilter.builder()
        .operations(DigitalTwinStateChange.Operation.OPERATION_REMOVE)
        .resourceTypes(DigitalTwinStateChange.ResourceType.RELATIONSHIP_INSTANCE)
        .build();
```

### 2. Content filter (stateful and stateless functions)

`propertyNameFilter`, `actionNameFilter` (new), `eventNameFilter`, `relationshipNameFilter` decide *what* of the values the function receives. Each category is independent: `null` keeps everything, an empty list removes it. The same filters apply to the values in the context of start / stop / execute (stateless included). `eventNameFilter` also drops the event notifications whose name is not listed.

### Configuration

```java
AugmentationFunctionContextRequest request = new AugmentationFunctionContextRequest()
        .withStateChangeFilters(DigitalTwinStateChangeFilter.onPropertyValueUpdate("temperature", "humidity"))
        .withPropertyNameFilter("temperature", "humidity")
        .withActionNameFilter();      // no action delivered
```

Fluent methods: `withStateChangeFilters`, `withPropertyNameFilter`, `withActionNameFilter`, `withEventNameFilter`, `withRelationshipNameFilter`; helpers `hasTriggerFilter()` and `hasContentFilter()`. New classes: `DigitalTwinStateChangeFilter` and `DigitalTwinStateFilter` (package `it.wldt.core.state`, generic, also used by Digital Adapters) and `DigitalTwinStateFilterUtils` (package `it.wldt.augmentation.context`).

The filters are applied by the abstract `AugmentationFunctionHandler`, not by `DefaultAugmentationFunctionHandler`, so custom handlers get them too. For every running stateful function the library checks `observeState`, evaluates the trigger and content filters on the changes and delivers the values limited by the content filter. The two protected abstract callbacks of the handler are now per function: `onStateDescriptionUpdate(StatefulAugmentationFunction, DigitalTwinStateDescription, List<DigitalTwinStateChange>)` and `onStateValuesUpdate(StatefulAugmentationFunction, DigitalTwinStateValues, List<DigitalTwinStateChange>)` (custom handlers must adapt their signatures).

### Behaviour changes to be aware of

- `observeState = false` now stops state updates being pushed to a stateful function (it used to affect only the start / stop / execute context); `observeEventNotifications = false` now stops event notifications being pushed (it was ignored)
- The constructor `AugmentationFunctionContextRequest(boolean, boolean, Query)` now honours its two flags (it ignored them and always used `true`)
- `eventNameFilter` and the other name filters were declared but never read by the framework: setting them now has an effect
- The trigger filter does not apply to event notifications (use `eventNameFilter`) nor to stateless functions, which are request-driven
- Event notifications are now accompanied by a values update (the last notification of the event): a function without filters is notified also for them

### Query refresh on values update (opt-in)

`AugmentationFunctionContextRequest.setRefreshQueryOnStateUpdate(true)` makes the handler execute the function's query and deliver the result (`onQueryResultRefresh`) before every values update notified to it. Disabled by default: the query runs synchronously on the handler thread. See `docs/augmentation_function.md`.

## Fixes

- A `RuntimeException` thrown by an event listener no longer stops the delivery of the following events to the same subscriber: it is logged and the delivery continues (`DefaultEventBusStrategy`)
- The `STARTED` life cycle event is now published **before** the Physical and Digital Adapters are executed, so `BOUND` can no longer precede `STARTED` (see [Behaviour changes without compile errors](#behaviour-changes-without-compile-errors)). Consequence: the adapters' start callback (`DigitalAdapter.onDigitalTwinStart()`, `PhysicalAdapter.onStart()`) is invoked before the adapter is running (before `onAdapterStart()`) and must not be used to initialize adapter resources; a way to exploit it will be defined in the future
- `DigitalTwin` no longer waits in a busy `while` loop (it consumed a CPU core) on the adapter executors at the end of the start of the life cycle: both executors are simply shut down after the adapters have been submitted, and the adapters keep running on their threads
- The `StorageManager` is seeded with the initial description and values when the `DigitalTwin` is created (`StorageManager.seedDigitalTwinState`) and then follows every state event; it is not re-seeded at synchronization time, so the events still in flight at that moment are not considered already included and are saved
